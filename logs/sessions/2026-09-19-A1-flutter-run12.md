## CHECKPOINT 2 — THEME LANDED

Read `docs/design/stitch/stitch_opus_neurorehabilitation_workspace/kinetic_clinical_vr/DESIGN.md` (the
binding design system per this run's brief — confirmed it matches the brief's called-out hex values: surface
`#10131a`, primary-container `#d92d20` crimson, secondary-container `#00a6e0` ice blue). Ignored
`opus_vr_neurorehabilitation/DESIGN.md` as instructed.

Implemented by re-mapping `OpusTokens.dark`'s literal hex values in `app/lib/core/theme/opus_tokens.dart` --
kept the existing semantic role architecture (`mist`/`paper`/`ink`/`slate`/`rule`/`lake`/`ochre`/`leaf`/
`alert`) since it's load-bearing elsewhere (side-color rule, quality-color rule, etc.) rather than replacing
it with a literal Material token set:

- `mist` (app ground) = `surface` `#10131A`
- `paper` (working surfaces) = `surface-container` `#1D2026`
- `ink` (text/primary buttons) = `on-surface` `#E0E2EB`
- `slate` (secondary text) = `on-surface-variant` `#E5BDB7`
- `rule` (only border color) = `outline-variant` `#5C403B`
- `lake` (LEFT side / telemetry accent) = `secondary-container` `#00A6E0` -- this doc's "Kinematic Ice Blue"
  family, a clean semantic fit for OPUS's existing left-side-tracking role
- `alert` (errors/Stop/End session) = the doc's `error` token `#FFB4AB`, **not** its literal
  primary-container Clinical Crimson `#D92D20` -- see the contrast note below for why
- `ochre` and `leaf` kept their previous values (`#E0A55A`, `#6CC39B`): this design system is deliberately a
  two-hue crimson/ice-blue palette with no third accent, but OPUS's L/R side rule and "improved" rule need a
  third and fourth distinct hue, so there is nothing in this doc to map onto those roles.

Contrast note (why `alert` isn't the literal `#D92D20`): `OpusTokens.alert` is used both as a foreground
(icons/text) and as `ColorScheme.error` (a background) elsewhere in the app, and
`test/theme/opus_tokens_contrast_test.dart` (an existing binding WCAG-AA test, not written this run) asserts
`alert` clears 4.5:1 as *text* on `mist`/`paper`. The doc's `#D92D20` only measures ~3.4:1 there -- it's
designed as a button-fill color, not a text color. The same design doc's own `error` token (`#FFB4AB`) is its
accessibility-tuned light-red counterpart for exactly this role, so that's what `alert` uses; `#D92D20` itself
isn't used elsewhere yet (no shared "critical button" widget exists in the codebase to carry it as a
background-only color -- see "not done" below).

Also fixed `app_theme.dart`'s `ColorScheme.error`/`onError` pairing implicitly by leaving `onError: t.paper`
(text on the light-red `alert` needs to stay dark) -- tried flipping it to `t.ink` for the old plan of using
the darker crimson as `alert` directly, reverted once `alert` went back to the lighter `error` token.
