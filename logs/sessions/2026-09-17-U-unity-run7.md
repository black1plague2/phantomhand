### Real bugs found (via the test failing, not by inspection) and root-caused

**1. Camera never actually pitched down (Opus's issue #1).** First attempt — set `CenterEyeAnchor.localRotation`
directly — measured correctly in-process and saved correctly to the `.unity` file (verified by grepping it), but a
**separate** batch process re-opening that same file read the rotation back as identity; the position half of the
same test passed on the same re-open, so this was rotation-specific. Second attempt — insert a wrapper GameObject
between TrackingSpace and CenterEyeAnchor and pitch the wrapper — broke `RigValidatorTests.Rig_HasExactlyOneEnabledCamera`
(found 2 enabled cameras). Third attempt — pitch TrackingSpace's own local rotation, no reparenting — camera count
stayed at 1, but the rotation STILL reset to identity on reopen. Conclusion: something under OVRCameraRig
(almost certainly `UpdateAnchors()`, plausibly running even in batch/no-device Edit mode) forces every anchor's
local rotation back to a neutral default absent live sensor data — this is about the **anchor subtree**, not
hierarchy shape. **Fix that stuck:** pitch the RIG ROOT ("[BuildingBlock] Camera Rig") itself — the GameObject
OVRManager/OVRCameraRig's own scripts live on, not one of the anchors those scripts drive. Its position edits had
already survived every prior run; empirically its rotation does too. Verified: `RigValidatorTests` 7/7,
`Eye_HeightAndDownwardPitch...` passes with measured `centerEyeWorldForward=(0.00, -0.50, 0.87)` = 30 deg down.
**Documented, accepted caveat** (same class as run7's rig-position workaround): a real headset's live head
tracking updates CenterEyeAnchor, not the rig root, so on real hardware this static pitch would compound with the
patient's own head tilt rather than being superseded by it. A real fix needs R4's calibration step to set this
from a live head pose, not a scene default — filed as a forward note, not fixed this run (out of scope: R4 shell
work).
**Side effect caught and fixed:** pitching the rig root also rotates children with LOCAL offsets, which shifted
`ChestReference`'s world Z from 0.00 to -0.11 (it was parented to the rig with a fixed local offset). Fixed by
setting ChestReference's WORLD position/rotation explicitly after parenting instead of a local offset — the chest
is a body-position reference and must not tilt with head gaze.
**Also required:** discarding a scene state corrupted by the reparenting experiment above — restored
`Assets/Scenes/OrchardReach.unity` via `git checkout` back to the clean committed baseline before re-applying the
working fix, rather than trying to hand-repair a scene with 3 stray duplicate GameObjects.

**2. Table/basket footprint dimensions were wrong (MODEL_REQUESTS.md's Y/Z axes swapped).** The table's top
surface came out at 0.846m instead of the placed 0.60m. Wrote a throwaway diagnostic
(`ImportMetaAssetsTool.DiagnosePivots`) that instantiates the wrapper + the raw source LODGroup mesh in isolation
and logs exact `Renderer.bounds` — real numbers, not the hand-typed MODEL_REQUESTS.md bbox column. Found: (a) both
`orchard_table` and `basket` meshes are natively **bottom-anchored** (min.y ~ 0), not Y-centered at origin as
`ImportMetaAssetsTool`'s pivot math assumed (the same bug class already fixed for the tree in run6, never
generalized); (b) MODEL_REQUESTS.md's Y/Z bbox columns are swapped for both — table's real height is 0.49m (not
the documented 0.60m) and its real footprint depth is 0.60m (not the documented 0.49m); basket's real height is
1.05 native units (not 1.99). Fixed at the root in `ImportMetaAssetsTool.Run()`: BottomCenter/TopCenter pivot
offsets are now computed from the model's actual measured post-scale local bounds, not a hand-typed
"NativeHeightUnits" constant — self-correcting for whatever the source mesh's real pivot turns out to be,
reproducing the tree's already-correct behaviour for free. Table/basket Z placement in
`OrchardSceneDressingTool` updated to the corrected 0.60m depth (table z 0.595 -> 0.65, basket z 0.40 -> 0.45).
**Also found:** `PlaceOrFind` (table/basket/tree placement helper) only set position/rotation on FIRST creation —
re-running the dressing tool after a placement-number tuning change silently did nothing on a scene that already
had these objects. Fixed to always re-apply position/rotation/scale.

**3. `DemoHandProxy_R` was tripling on every dressing-tool re-run.** Found 3 stray, all-disabled
"DemoHandProxy_R" GameObjects in the pre-run8 scene file. Root cause: `GameObject.Find` never matches an
**inactive** GameObject, and the old code called `SetActive(false)` on it right after creating it — so every
re-run's "does it already exist" check failed and created a new duplicate. Fixed by (a) looking it up via
`Resources.FindObjectsOfTypeAll` (which does see inactive objects), destroying any extras found, and (b) hiding it
via its Renderer instead of `SetActive(false)` — a MeshRenderer toggle `GameObject.Find` doesn't care about.

**4. Apple showed jagged black/green texture patches close-up (Opus's issue #2) — root-caused, not lighting.**
`SeatedLayoutTests` confirmed the fruit_apple PREFAB's assigned material is correctly the 12913 apple (not the
632623 distractor) — so the defect had to be something dynamic. Traced via `ImportMetaAssetsTool.RepointMaterials`:
it matched each LOD level's material by looking for "_L"/"_M"/"_S" in the renderer's **GameObject name** — but the
LODGroup prefab's actual per-LOD GameObjects are named "LOD0"/"LOD1"/"LOD2" (confirmed by reading
`12913_LODGroup.prefab` directly), which never matches that pattern. Every LOD silently fell through to the
"single-LOD fallback" and got the L (highest-detail) material forced onto it, INCLUDING LOD1/LOD2, whose meshes
have their own different UV layout baked for their own M/S texture. Unity switches to a lower LOD at the screen
size a 7cm apple viewed from ~0.3-0.5m triggers — exactly the close-up PlayMode shots — so those were rendering an
M/S mesh wearing the L texture through mismatched UVs: the scrambled/blocky black/green look. Fixed by reading the
LOD suffix off the renderer's **original (pre-repoint) material name** instead — the source MetaAssets materials
are correctly named `<assetId>_L`/`_M`/`_S`, a reliable signal that was sitting there unused. Re-ran
`ImportMetaAssetsTool.Run()` (note: this wipes any grabbable-component setup `OrchardSceneDressingTool` had
already added to the prefab root, since it saves a fresh root as the whole prefab — re-ran
`BatchDressOrchardScene` afterward to restore Rigidbody/Collider/HandGrabInteractable, confirmed via its own
`[OPUS] verify fruit_apple` log line). Confirmed fixed by direct visual inspection of fresh screenshots (below) —
apple renders as a clean red apple with its stem/leaf at every distance now, no black/green patches in
`01_target_shown`, `03_grasp`, or `04_placed_in_basket`.
