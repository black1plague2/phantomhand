## CHECKPOINT 1 — root-cause findings + fix so far

### Root cause (Task 1: zero haptic_cue / form_warning events in run9's demo)

Confirmed via code read, not guesswork:
- `FormFeedback` (Packages/com.opus.sdk/Runtime/Feedback/FormFeedback.cs) is correctly constructed and
  subscribed (`_formFeedback.OnSignal += HandleFormSignal;` in `OrchardReachSceneController.Awake()`), the lean
  is computed relative to the trial-start head pose (or, in demo mode, via the scripted `_demoSessionElapsedMs`
  window — session-wide, not per-trial, already fixed by a prior run's comment), and `hapticsEnabled` is set
  true via `ConfigureHapticsForTest` in every test that needs it. All the things the brief asked me to check on
  FormFeedback's side are fine.
- The actual break is in **`UdpHapticTransport`** (Packages/com.opus.sdk/Runtime/Transport/UdpHapticTransport.cs):
  its discovery listener binds a **fixed** UDP port (8791, not ephemeral) in a background `Task` started from
  `Start()`. `OrchardReachSceneController`'s teardown (`OnDisable`/`OnDestroy`/`OnApplicationQuit`) only ever
  called `HapticClient.Stop()` — which just sends a device-level "stop" datagram — **never**
  `HapticClient.Dispose()` / `IHapticTransport.Dispose()`, which is what actually cancels the discovery task and
  closes the sockets. Since NUnit's Test Runner reuses one process/domain across all PlayMode tests in a run
  (no domain reload between them), every scene reload (`EditorSceneManager.LoadSceneInPlayMode`, called once per
  test) constructs a brand-new `UdpHapticTransport` in the new `OrchardReachSceneController.Awake()`, whose
  `DiscoveryLoopAsync` tries `new UdpClient(8791)` — which throws (port still held by the PREVIOUS test's
  never-disposed transport), is caught, logged, and the discovery loop exits immediately. Net effect: only the
  **first** PlayMode test in a session can ever discover the sleeve; every later one has `HasDevice` permanently
  false, so `HapticClient.GateCue` silently drops every cue (`if (!_transport.HasDevice) return false;`) even
  with `sim/haptic/fake_haptic.py` alive and broadcasting `hello`. This exactly matches run9's observed
  `run9_playmode3_results.xml`: `DemoSession_WithSleeve_...` (3rd test in the fixture) got `cueOrder=[]`.

  **Fix applied**: `Assets/Shell/Runtime/OrchardReachSceneController.cs` — `OnDestroy` now also calls
  `_haptic?.Dispose()` (which disposes the transport: cancels the discovery task, closes both UDP sockets) in
  addition to the existing `StopHapticsSafely()`. Left `OnDisable`/`OnApplicationPause` sending only the safety
  `stop` message (unchanged) since those must stay resumable, not tear down the link.

  **Result after fix**: EditMode 107/107 green (see below). PlayMode: `DemoSession_HapticsDisabled_SendsNoCues`
  still passes; `DemoSession_WithSleeve_ProducesOrderedCuesAndValidSession` **still shows `cueOrder=[]`,
  trunk_lean=0`** in run10's first PlayMode pass — the port-leak fix alone was not sufficient; investigating
  further (next: log whether `OnDeviceKnown`/discovery ever actually fires post-fix, i.e. whether the demo's
  600ms lean window is simply too short relative to real discovery latency even on a clean port, since
  `fake_haptic.py`'s `_hello_loop` sends its first beacon immediately but the C# discovery `Task.Run` scheduling
  + Awake()-time transport `Start()` + the 0.5s pre-scene-load sleep leave less margin than assumed). Continuing
  to diagnose before the next batch run.

- **`DemoSession_SleeveNeverAnswers_SessionStillCompletes`** is very likely a *separate*, non-haptics bug: the
  demo replay fixture (`contracts/fixtures/sessions/healthy/kin_*.json`) is only 4 chunks × 360 frames = 1440
  frames, i.e. ~20s of unique motion at the demo's 72Hz playback clock (`DemoFrameDtMs`). `SyntheticHandDriver`
  freezes at its last frame once `Finished` (by design, does not loop) instead of continuing to produce fresh

  fixture in `SyntheticHandDriver` instead of freezing) but **not yet applied** — still deciding whether this is

## CHECKPOINT 3 -- #3's REAL root cause found (test-harness bug, not FormFeedback/HapticClient)

Added per-instance diagnostics (_haptic.GetHashCode() + GetInstanceID()) to HandleFormSignal and
ConfigureHapticsForTest, ran once (run10_playmode7.xml), and got an unambiguous answer -- see the exact
line-numbered timeline pulled from run10_playmode7.log:

```
2701 Test Started: DemoSession_HapticsDisabled_SendsNoCues
2819 ConfigureHapticsForTest  controllerId=56512   <- Test 1's (OrchardAudit) LEFTOVER controller
2846 HandleFormSignal          controllerId=90324   <- Test 2's OWN, real, never-configured controller
...
3044 Test Started: DemoSession_SleeveNeverAnswers_SessionStillCompletes
3162 ConfigureHapticsForTest  controllerId=90324   <- Test 2's controller, configured one test late
3189 HandleFormSignal          controllerId=90514   <- Test 3's OWN, real, never-configured controller
...
3469 Test Started: DemoSession_WithSleeve_ProducesOrderedCuesAndValidSession
3587 ConfigureHapticsForTest  controllerId=90514   <- Test 3's controller, configured one test late
3614 HandleFormSignal          controllerId=90704   <- Test 4's OWN, real, never-configured controller (Enabled stays False for its entire 40s life)
```

Root cause: HapticIntegrationTests.LoadSceneAndGetController() called GameObject.Find(...) on the SAME line as
EditorSceneManager.LoadSceneInPlayMode(...), with no yield in between. That scene load is NOT synchronous -- the
actual unload/Awake() swap happens on a later Editor update tick -- so Find reliably returned the PREVIOUS
test's still-alive controller, one test late, every single time. Every call site already did
`yield return null; yield return null;` right AFTER calling this method (specifically to let the load finish)
-- but by then the stale reference was already captured in `controller`. Net effect: every test's
ConfigureHapticsForTest(...) call was configuring the WRONG (previous test's, about to be torn down)
controller, while the REAL controller driving that test's Update()/FormFeedback/HapticClient for its entire
lifetime kept the manifest default Enabled=false -- so trunk_lean/low_confidence signals fired correctly
(confirmed clean edges in earlier checkpoints) but every SendTrunkLean/SendLowConfidence call hit GateCue's
`!Enabled` branch and was dropped, forever, for that test. This fully explains cueOrder=[] despite the sleeve
being discovered and FormFeedback behaving correctly -- items (a)-(d) of Opus's own diagnosis list for failure
#3 (same head transform, amplitude vs threshold, >300ms hold, reference not re-captured mid-spike) were all
already fine; the bug was one level up, in the test harness's scene-load timing, not in
FormFeedback/HapticClient/the demo trigger logic at all.

Fix: HapticIntegrationTests.cs -- LoadSceneAndGetController is now a coroutine
(IEnumerator LoadSceneAndGetController(Action<OrchardReachSceneController> onReady)) that issues the load,
yields twice, and only THEN does GameObject.Find -- guaranteeing the new scene has actually finished loading
first. All three call sites updated to `yield return LoadSceneAndGetController(c => controller = c);`. Removed
the temporary per-instance (hapticHash/controllerId) debug lines from OrchardReachSceneController.cs now that
the bug is identified and fixed (kept the lower-volume, genuinely useful GateCue-drop-reason and
"sending cue=" / "sleeve discovered" diagnostics in HapticClient.cs/UdpHapticTransport.cs -- they cost nothing
and match HAPTIC_PROTOCOL.md's own auditability framing).

Also checked: OrchardReachPlayModeAuditTests.cs (failure #1, the basket test) does NOT have this bug -- it
already does `yield return null; yield return null;` BEFORE its own GameObject.Find, inline in the test body
(no separate synchronous helper). So failure #1 is a genuinely separate, real bug in the game module's own
settle/placement geometry, not a test-harness artifact -- still open, per Opus's ask, investigating next without
loosening the assertion.

Not yet run again -- that's the immediate next step.
