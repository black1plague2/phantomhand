## What the firmware author answered (18:09) and what it changed

The full table is `docs/PH_ELECTRONICS_HANDOFF_FROM_TEAM.md` §C. The one that mattered:

**Acks go to the port a command came from; `sensor_data` and `sensor_chunk` go to the FIXED port 8790 of the last
sender's IP.** The game (`UdpHapticTransport`: one socket on an ephemeral port per node) and the Python stand-in
(`NodeLink`) listened only on the port they send from. Against the real boards they would have had acks and no IMU, no
EMG: no flinch measure, "Node B absent" on the phone. Every simulated run was green because the twin's team dialect
streamed to the sender's source port.

Fix, software only (the firmware stays):

| Where | Change |
|---|---|
| `game/Packages/com.opus.sdk/Runtime/Transport/UdpHapticTransport.cs` | optional `telemetryPort`; new `TelemetryHub`: one shared UDP socket per port, a datagram goes to the transport whose node sent it (exact ip:port, else the only transport on that IP); deliveries to one transport are serialised |
| `game/Assets/Shell/Runtime/PhantomEndpoints.cs`, `PhantomHandSceneController.cs` | the Phantom Hand scene listens on 8790 by default; `OPUS_PH_TELEMETRY_PORT` moves it for a simulator on the same PC |
| `game/Assets/Shell/Tests/PlayMode/PhantomHandFullRunTests.cs` | the test's own twin now speaks the team dialect with a telemetry port (`OPUS_PH_TWIN_DIALECT=reference` gives the old one); the fault flags of `tools/demo/unity_fault_run.py` |
| `contracts/HAPTIC_PROTOCOL.md` v1.3, `contracts/schemas/haptic-message.schema.json` (description only) | rows "Telemetry port", chunk stamp = last value, messages the firmware does not send, cue form |
| Python (`sim/sleeve/twin.py`, `sim/live/phantom_replay.py`, `tools/demo/*`) | see "Python side" below |

`sensor_chunk.timestamp_ms` is the LAST value's time on this firmware (the contract said first). No code change: the game
anchors a chunk at its arrival and counts back from its last sample (`SleeveSensorClient.ParseSensorChunk` with the median
offset of `ClockOffsetEstimator`), so the stamp convention cancels out. Shown by algebra in the code comment, not yet by a
measurement on the wire.

## The phone app's live card after a reconnect (found 20:10, fix in work)

Tests written by a Sonnet builder with a real WebSocket headset through the real provider, repository and model (`app/test/hub/`,
`app/test/phantom/`): after a headset reconnect the Phantom Hand card comes back with a fresh model 250 to 300 ms later, and the
headset's replay has already passed, so the witness numbers, the closing lines and the markers are missing ("Expected: not null /
Actual: <null> ... no witness numbers on the card after the reconnect"). The hub-level behaviour is as read (the echoed
`resume_from_seq`, replays reach listeners again); with the same replay sent once the card is back, the card is complete, so its
consumers are idempotent. Whole Flutter suite at that point: "+484 -2", the two failures being exactly those findings. A fix inside
`app/lib/features/live` is being written; `contracts/LIVE_PROTOCOL.md` ("Known deviation") still says the card is rebuilt by the
replay, which these tests disprove: to be corrected with the fix.
