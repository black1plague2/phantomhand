## CHECKPOINT 3 — a SIXTH "shape not meaning" defect, found by running analytics for real

Task 6 says to re-confirm the five known defects. Doing that on the newest recorded session found a
**sixth one that all five fixes and every schema run missed**, and it is game-side (my track).

Session used: `%LOCALAPPDATA%\LocalLow\DefaultCompany\OPUS\opus_sessions\cb77b474-...` (2026-09-19 04:43).

```
  [PASS] events.ndjson: 77 events validated
  [PASS] kin_000.json .. kin_005.json
  [WARN] metrics.json not found
  [PASS] All validations passed

```

Schema-clean. Then actually running analytics on it:

```
analytics\.venv\Scripts\python.exe -m opus_analytics <that dir>
  File "opus_analytics\kinematics.py", line 15, in slice_window
    return {"t_ms": t[idx], "pos": joint["pos"][idx], "conf": joint["conf"][idx]}
IndexError: index 925 is out of bounds for axis 0 with size 925
```

**Root cause (game-side, `game/Packages/com.opus.sdk/Runtime/Recording/KinematicsRecorder.cs`).**
`kinematics-chunk.schema.json` states the invariant in its own description — *"each array length == t_ms
length. conf 0 = not tracked"* — but JSON Schema cannot express a cross-array length equality, so nothing
enforced it. `Sample()` appended to `t_ms` once per distinct timestamp, but appended to a joint's
`pos`/`conf` only on frames where that joint was actually passed in. `OrchardReachSceneController.
TrySampleJoint` deliberately **skips** untracked joints ("so a gap reads as a gap instead of a real pose
at the origin") — a reasonable-sounding decision that silently desynchronises the columns. A joint first
seen on frame 30 had its first sample attributed to `t_ms[0]`.

Measured, per joint, across every session on disk:

```
session cb77b474 : t_ms 1060 frames, r_* joints 925 (87%), l_* joints 848 (80%)   -> analytics CRASHES
session c93ae4fa : t_ms 1461 frames, r_* joints 1455 (100%), l_* 1423 (97%)       -> off by 6 frames
worst-joint coverage over all 10 sessions on disk: 1%, 1%, 17%, 18%, 19%, 35%, 39%, 76%, 92%, 99%
```

Two consequences, in order of severity:
1. analytics crashes outright when the shortfall is large — no biomarkers at all;
2. **where it does not crash, it is worse than a crash**: every position after the first dropout is
   paired with the wrong timestamp, so velocity, peak speed, SPARC and LDLJ are computed on a corrupted
   time base while every file still passes `validate.py`. This is exactly the CONTEXT.md failure class.

Note for Opus, honestly: `c93ae4fa` is the session CONTEXT.md holds up as the verified reference
("RT 250–1304 ms, peak 1.3–2.1 m/s, SPARC −2.0…−3.4"). Its right hand — the analysed side — was 6 frames
short of 1461, so those numbers are close to right but were **not** computed on a fully aligned series.
They should be regenerated from a post-fix session before being quoted again.

**Fix applied** (`KinematicsRecorder.cs`): `t_ms` is now the authoritative frame axis and every joint
series is kept exactly parallel to it. A new timestamp closes the previous frame and pads every joint
that did not report; a joint discovered mid-chunk is back-filled; `Flush()` pads the final frame. Padding
uses `conf 0` — the schema's own encoding for "not tracked" — carrying the last pose forward as an inert
placeholder, so a padded sample can never be mistaken for a real one (analytics gates on `conf`). A joint
sampled twice in one frame now overwrites rather than desynchronising.

**Regression test added** (`com.opus.sdk/Tests/Editor/KinematicsRecorderTests.cs`):
`EveryJointSeriesStaysParallelToTMs_EvenWhenJointsDropOutOrStartLate` — reproduces the exact shape that
broke it (a joint present throughout, one that drops out for frames 10–19, one first seen at frame 25)
and asserts every series is `t_ms`-length, gaps are `conf 0`, and real samples stay on their own index.
