## The four run-10 gaps

1. **No trunk-lean vignette or audio existed at all.** This is the *primary* feedback — haptics are
   additive, so without it a patient with no sleeve got nothing. New
   `Assets/Shell/Runtime/TrunkLeanVignette.cs`: a quad parented to the eye anchor, alpha ramped over
   ~150 ms, radial falloff that tints only the outer ~45 % of view (it can never obscure the reach
   target), driven **directly off `FormFeedback`'s polled state, never through `HapticClient`** — so it
   works with haptics off and with no sleeve. Audio is a procedurally generated soft sine tone
   (attack/release envelope, no click), rate-limited to the protocol's 800 ms trunk-lean gap. A separate,
   distinctly coloured and positioned soft badge covers the low-confidence "hand out of view" cue.
   A URP `ScriptableRendererFeature` would be the textbook answer but needs a renderer-data asset edited
   outside batch-mode script access; a scene-space quad is provably visible in the batch capture path.

2. **Debug cyan sphere visible behind the ghost hand.** It is the 3 cm index-tip *marker* from before
   there was a hand mesh — and it is still the authoritative transform (the ghost hand is offset from
   `demoHandProxyR.position`, and the audit/seated-layout tests assert on it), so it must keep moving.
   Only its **renderer** is now suppressed, and only when a real hand mesh is present; with no ghost
   prefab it stays visible as the documented fallback.

3. **`low_confidence` double pulse fired both taps at once** (spec: 120 ms apart). `HapticClient` now
   schedules the second pulse on a `_scheduled` list drained by `Pump(nowMs)` — non-blocking, no
   `Thread.Sleep`, so the caller's frame is never held. Test asserts nothing at 119 ms, second pulse at
   120 ms.

4. **Basket "near-miss" (10.28 cm in run 10).** Two separate causes, one real and one measurement:
   - Real: the demo carry/release path is entirely script-driven, but the fruit rigidbody was never
     kinematic, so gravity accelerated it every `FixedUpdate` while parented to the moving hand, which
     Unity resolves as silent local-position drift. Kinematic **in demo mode only** (the real
     HandGrabInteractable path manages its own kinematic state). Release distance went 10.28 cm -> 1.9 cm.
   - Measurement: the audit test sampled the apple one polled frame *after* `placed`. By then
     `ConfirmPlacedInBasket -> OnTrialFinished -> next trial's target_shown` had already repositioned that
     same FruitInstance onto the next target (an apple on a tree, y ~0.83). **Run 10's 10.28 cm and run
     11's first 3 cm failure were both measuring the next trial's target, not the placement.** The test
     now captures the position inside the `placed` callback: `inside=True`, apple at y 0.65 in bounds
     [0.62, 0.80].

## Four bugs Opus found in the run-11 agent's own uncommitted code

1. **`Destroy()` from edit mode.** `TrunkLeanVignette` destroys the primitive's collider during
   `Awake`, and `SeatedLayoutTests` invokes `Awake` by reflection in EditMode, where `Destroy` is an
   error. EditMode was 106/107. Fixed with a `SafeDestroy` helper (`DestroyImmediate` when not playing).
2. **Haptic discovery race — every cue silently dropped.** With the sleeve present the run produced
   `cueOrder=[]`: the demo's scripted cue windows start counting at scene load, while `UdpHapticTransport`
   only learns the sleeve's address from its once-per-second broadcast. Discovery landed *after* the
   600 ms lean window closed, so each cue was dropped with "no haptic device known yet". Run 10 passed on
   luck. The demo windows now wait until the haptic path is ready, with a **3 s grace ceiling** so the
   demo never depends on hardware: haptics off, or a sleeve that never answers, behaves exactly as before
   (G10). Real sessions don't use these windows; a genuine lean before discovery still gets vignette+audio.
3. Seated-layout test asserted the *marker* was drawn; it now asserts the ghost mesh is visible **and**
   the marker is hidden, so it keeps testing "the patient can see a hand" rather than one legacy object.
4. `logs/CHANGELOG.md` held one stray cp1252 `§` byte (invalid UTF-8) — repaired.

## Iteration 2 (Opus, 2026-09-19): the vignette was real but invisible, and two tests were flaky

Committing `d88e1b1` was not the end. Shooting the screenshot exposed more.

**The vignette rendered but could not be seen — three separate causes, found one at a time.**
1. **Captured mid fade-in.** The first capture fired on the lean's first active frame: alpha **0.002**. The
   PNG was indistinguishable from "no vignette exists", and my own `IsRendering` check (alpha > 0.001)
   passed it. Added `Alpha`, and the test now waits for alpha >= 0.30 and asserts it.
2. **The falloff sat outside the frame.** The quad was sized for a "generously large" 110 deg / 2.2 aspect.
   That is backwards for a radial falloff keyed to the quad's own extent: the camera's real ~90 deg / 1.78
   frustum then only saw the quad's inner region, which the falloff keeps fully transparent. The warning
   border was rendering off-screen. The quad is now fitted to the camera that looks through it.
3. **Fitting it exactly showed the quad's own border** as a hard vertical seam (the eye camera reported 4:3
   while the capture target is 16:9). The quad now overshoots the frame, and the falloff is computed in
   **frame-normalized** coordinates so it still reaches full strength at the frame edge. Measured against the
   quad instead, the tint was ~5 % opacity at the edge of view — present in the render, useless as a cue.

**Confirmed visually:** `logs/sessions/screens/unity/run11/during_trunk_lean.png` — an amber border framing
the view with the apple, hand, basket and table left completely clear. The cyan debug marker is gone.

**Two tests were flaky, and the green run that justified `d88e1b1` was luck.** Re-running the suite failed
both again:
- *Release distance* read 0.019 m, then 0.000 m, then **0.218 m** across otherwise identical runs. The glide
  drives the *hand* to the release point and the apple rides along as a child, so the apple lands at the
  target plus whatever hand->apple offset that run's grasp captured. The demo release is scripted, so the
  apple itself is now placed on the release target.
- *trunk_lean never fired* again: discovery landed after the 3 s arming grace (it picked a link-local
  169.254.x.x route that run), so the cue was correctly dropped as undeliverable. Dropping it is right for the
  product (G10, fire-and-forget) and useless for a test, so the test now waits for `Haptic.Connected` and
  re-arms the demo clock before measuring.

**Environmental:** one batch run died with exit 139, crashing inside `XrApiLayer_METAX_operator` (the Meta XR
OpenXR API layer), not in project code. A plain retry succeeded. Expect this occasionally.
