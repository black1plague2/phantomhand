## CHECKPOINT 9b: Opus task #2 — grasp/carry/release/settle are geometry-driven, not scripted-independently

**Files:** `Assets/Shell/Runtime/OrchardReachSceneController.cs`,
`Assets/Games/OrchardReach/Tests/PlayMode/OrchardReachPlayModeAuditTests.cs`.

Root cause (confirmed by reading the code, not guessed): `OrchardReachModule.IsGraspOverTarget` /
`GraspDetector` only ever look at **pinch-strength timing** from the raw fixture data — never hand position —
so the module's `Grasped` event fires on a schedule baked into the recording, with zero coupling to where the
demo hand-proxy sphere or the fruit visually were. Run8's fix (glide the FRUIT toward the basket once grasped)
only fixed the fruit's path; it never reconciled the HAND's visual position with either the fruit or the
module's own grasp event — exactly Opus's "events are scripted, not contact" finding, confirmed by run8's own
screenshot description ("hand proxy sphere sits near a table leg... not yet moved toward the target").

Fix, replacing run8's two-independent-paths design with one coupled state machine in
`OrchardReachSceneController.DriveDemoHandAndFruit` (called every frame, after `_module.Tick`, so it reacts to
state transitions the same frame they happen):
- **Reach** (`TargetShown`/`MovementOnset`): the hand-proxy marker's position is retargeted every frame —
  `Lerp(reachOnsetPos, currentApplePos, t)` where `t = clamp01(rawPinchStrength / GraspDetector.PinchThreshold)`
  — the SAME raw pinch signal the module uses to decide when to fire `Grasped`. Since `Lerp(a,b,1) == b` exactly
  regardless of overshoot, the index-tip marker is **exactly** at the apple's position by the time `t` reaches
  1, which happens at essentially the same instant the module's threshold-crossing fires `Grasped`.
- **Grasp** (state becomes `Grasped`/`Holding`, first frame): snap the marker exactly onto the apple's position
  (distance = 0, trivially `<= 0.05m`) and **reparent the fruit onto the hand marker** (`SetParent(...,
  worldPositionStays: true)`) — one motion carries both from here on, not two independently scripted paths.
- **Carry**: the hand marker (with the attached, child fruit) glides over `HoldGlideDurationMs=900ms` to a point
  computed from the basket's OWN measured `Collider.bounds` (`AboveBasketPoint()` =
  `(bounds.center.x, bounds.max.y + 0.08, bounds.center.z)`) — not a hand-typed constant, matching this
  project's established "measure the real asset, don't guess" discipline (same class as run8's pivot-math fix).
- **Release** (glide reaches t=1): the fruit is unparented at that above-the-basket point;
  `LastReleaseWorldPos` (new public `Vector3?` property) records it for tests. `HandleTrialEvent`'s
  `target_shown`/`trial_start` handler now unconditionally detaches the fruit and resets this whole state
  machine at the start of every trial — needed because the module can end a trial early via its own
  grip-relax-drop path mid-carry, which would otherwise leave the fruit still parented to the hand while a new
  trial's target-shown handler tried to reposition it.
- **Settle**: runs independently of trial state (so a same-frame trial-finish doesn't strand it) — the
  unparented fruit glides over a separate, short `SettleDurationMs=250ms` from its release position into
  `InsideBasketPoint()` (`(bounds.center.x, min(bounds.min.y+0.03, bounds.max.y), bounds.center.z)`), which is
  what lets `BasketTrigger`'s real `OnTriggerEnter` physics fire "placed" once the fruit's collider actually
  crosses into the basket's volume — same detection path as run8, just aimed at a real in-bounds destination
  instead of a hand-typed guess (run8's `up*0.12` constant).

New PlayMode assertions in `OrchardReachPlayModeAuditTests` (hard-fail if the corresponding state is observed at
all — soft-warn only if the whole state is never reached within the 30s budget, same discipline as the existing
grasp/placed warnings):
- At grasp: `Vector3.Distance(handMarkerPos, applePos) <= 0.05m`.
- At release (`LastReleaseWorldPos` first becomes non-null): horizontal distance to basket-bounds center
  `<= 0.10m`, and `apple.y > basketBounds.max.y` (above the rim).
- At the real "placed" event: `basketBounds.Contains(applePos)` (inside the basket).

Also added a 5th capture, **`04_carry`** (first frame the apple is observed parented to the hand mid-Grasped/
Holding), between grasp and placement, renaming the old `04_placed_in_basket` to `05_placed_in_basket` and the
output directory from `run8_playmode` to `run9_playmode`, per the brief's "01..05" naming.

**Not run this session**: none of these numbers are measured yet. Known risk carried over from run8's own design
(not something this run introduced): the module can independently end a trial as "Dropped" if the raw fixture's
own pinch strength drops below `GraspDetector.WholeHandThreshold * 0.5` while `Holding`, before the carry+settle
finishes — run8's original 900ms glide already survived this once (`successCount=1`), and this run keeps the
same 900ms carry duration (only adding a short extra 250ms settle) to keep that risk about the same, but this
is reasoning from the code, not a fresh measurement.

**Final implementation:** `OrchardSceneDressingTool.DressOrchardScene` now instantiates

(`DemoHandProxy_R_GhostHand`, idempotent create-or-find, hidden via `Renderer.enabled=false` until posed, same

from `DriveDemoHandAndFruit`) positions it at the wrist (retargeted by the same rigid offset as the index-tip
marker, so the whole hand visual moves with wherever the marker has been retargeted/carried) and orients it via
`Quaternion.LookRotation(wristToIndexDirection, Vector3.up)`.

**Verified, not assumed, why "oriented by the recorded wrist rotation" literally cannot be done**: read
`contracts/fixtures/sessions/healthy/kin_000.json` directly (via a throwaway Node script, not a guess) —
`frames.r_wrist.rot` is absent from the JSON entirely (`JointSeries.Rot` is a nullable field; this fixture's
`rot` key is simply not present, confirmed for every joint in the file, not just the wrist). `KinematicsChunk.cs`
already documents `Rot` as optional (`NullValueHandling.Ignore`), and `SyntheticHandDriver.TryGetJointPose`
correctly returns `rotQuatXyzw = null` for this dataset (visible in its source — `series.Rot != null &&
_frameCursor < series.Rot.Count ? series.Rot[_frameCursor] : null`, and `series.Rot` itself is only allocated
when the SOURCE chunk had a non-null `Rot` list). **There is no recorded wrist rotation anywhere in this
project's demo fixture data to orient by.** The heading used instead (wrist -> index-tip direction) is a
documented approximation, not the literal instruction, because the literal instruction assumed data that does
not exist. This is written up in the code (`DriveGhostHandVisual`'s doc comment) exactly as above, not silently
substituted.

Also documented (same doc comment): this remains a single static mesh, not a per-finger-posed grasp shape — a
true rigged/posed hand needs the ISDK/OVR synthetic-hand data pipeline this project has already deferred
(`docs/UNITY_PRACTICES.md` §6) for the identical "needs a connected Interaction SDK to build/verify against,
infeasible in a headless/batch session" reason `SyntheticHandDriver`'s own header comment gives.
