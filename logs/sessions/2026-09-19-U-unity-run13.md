## CHECKPOINT 2 — TASK 2 fix (grasp screenshot timing)

Root cause found in `Assets/Shell/Tests/PlayMode/FullPipelineIntegrationTests.cs`: the capture fired on
the literal first frame `state == TrialState.Grasped`. `OrchardReachSceneController.DriveDemoHandAndFruit`
(Assets/Shell/Runtime/OrchardReachSceneController.cs, Grasped/Holding branch, ~line 673) snaps the hand
marker's position exactly onto the apple's position on that same frame, then parents the apple to it —
so at the captured instant hand and apple are exactly concentric, and the apple renders behind/inside the
(unrigged, open-palm) hand mesh instead of looking "held".

Fix:
- Added `public double HoldGlideElapsedMs` to `OrchardReachSceneController` — real ms elapsed since the
  current Grasped/Holding carry glide began (-1 outside that phase).
- `FullPipelineIntegrationTests` now waits for `state is Grasped or Holding` AND
  `HoldGlideElapsedMs >= 350.0` before firing "02_grasp" — 350 ms is safely inside the carry window
  (HoldMs default 300 ms so Grasped→Holding transitions before this fires; HoldGlideDurationMs is 900 ms so
  there's still ~550 ms of glide left, well before release/detach), by which point the hand has visibly
  separated from the tree/table, carrying the apple.

Not yet verified by an actual test run (needs a live hub on :8787 + optionally the sleeve sim on :8790,
which this run has not started) — will attempt in the pipeline-run step; if no hub is available, this fix
is reviewed by inspection only and documented as such.

## CHECKPOINT 4 — LOD diagnostic results: the two visible trees are NOT the cause

Ran the (fixed, rig-hidden) diagnostic in batch edit-mode: `logs/sessions/run13_lod_diag2.log`, screenshots in
`logs/sessions/screens/unity/run13_lod_diag/{lod_auto,lod0_forced,lod1_forced,lod2_forced}.png`. I read all
four with the Read tool.

Found 5 LODGroups in the static dressed scene: `OrchardTable`, `[BuildingBlock] Camera Rig`,
`OrchardTree_2`, `OrchardTree_1`, `Basket` — all imported-asset LODGroups with 3 levels each
(screenRelativeHeight 0.5/0.2/0.05), all reporting ~2.0-unit sizes (the Meta asset library's normalized
bounding box before each wrapper prefab's own scale is applied).

Result: **lod_auto and lod0_forced are visually identical to run12's real screenshot** (full detail on both
trees, no sliver). **lod2_forced (lowest detail) shows degenerate, twisted diamond-shaped leaf geometry on
both trees** — an ugly separate bug (leaf-card LOD decimation collapsing into flat shards) but NOT the
sliver: it's symmetric leaf clutter across both trees' whole canopy, not one stretched shape hanging in open
air between them. **Ruled out: the two visible trees' LODGroups are not the sliver's source.**

Root-caused the gap instead: `DemoHandProxy_R_GhostHand` (the `ghost_hand_static` asset, aka Meta asset
286115, posed every frame by `DriveGhostHandVisual` during a reach) has its own LODGroup
(`Assets/MetaAssets/Prefabs/286115/286115_LODGroup.prefab`, confirmed via the same guid-chase used for the
tree). My static edit-mode tool never found it: reading `Assets/Scenes/OrchardReach.unity` directly shows
`DemoHandProxy_R_GhostHand` is a PrefabInstance parented under the building-block rig with its own
MeshRenderer components individually disabled (`m_Enabled: 0`, matching `OrchardSceneDressingTool`'s "shown
by the controller once it starts posing it") — but more importantly its ancestor chain under
`[BuildingBlock] Camera Rig` only activates once the rig initializes, which does not happen outside Play
mode, so `FindObjectsByType<LODGroup>` in a static edit-mode capture silently skips it. This is the reason
the sliver never showed up in any of the four edit-mode screenshots above: **the object it plausibly belongs
to was never even in that capture.**

Wrote a second, PlayMode diagnostic test (`Assets/Shell/Tests/PlayMode/SliverDiagnosticTest.cs`, temporary,
same disposal note as the Editor tool) that loads the scene for real, waits for `TrialState.MovementOnset`
(exactly the state 01_mid_reach.png captures), lists every ACTIVE LODGroup at that point (should now include
the ghost hand's), and forces the ghost hand's LODGroup through LOD0 and LOD2 with a capture at each, to see
whether the sliver tracks it. Filtered PlayMode run in progress (`-testFilter SliverDiagnosticTest`) — result
in the next checkpoint.
