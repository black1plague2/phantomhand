Rebuilt + reinstalled APK, then ran the real mock headset (`sim/live/fake_headset.py --generate --stage reach
--trials 6 --host 172.17.221.245 --port 8787 --no-scenario`, matching S's current `--help` flags) against the
phone's hub. **Found a real bug this surfaced, not just a UI gap**: with `--no-scenario` the fake headset
correctly connects (RTT ~10-50ms, real ping/pong) but times out after 30s waiting for a `start` command --
because nothing in the app ever sent one (no auto-start, and my blind on-device taps at the Devices "Start"
button kept missing the 30s window by 1-2s each of 3 attempts -- tool-call round-trip latency, not an app bug;
logged for honesty). Re-ran **without** `--no-scenario` (headset plays through immediately, which is how
`sim/live/fake_headset.py --help` documents that mode, and is realistic since the real Unity `OpusSessionRunner.cs`
per `CONTEXT.md` also just streams status/trial_event/metrics_tick on its own, no server-issued `start` in
that direction) -- headset connected and streamed real `trial_event`/`status`/`metrics_tick` traffic (confirmed
in its log, seq climbing past 300+ within 2s), but the Monitor tab kept showing "Headset connected, no session
running yet" the whole time.

Root-caused in `app/lib/core/hub/hub_connection.dart` (my scope, `core/hub/**`): `_onData`'s switch set
`activeSessionId` only on the wire-level message `type` literally equal to `'session_started'`/`'session_ended'`
-- real, schema-valid values (`contracts/schemas/live-message.schema.json` line 14), but **nothing that
actually talks to this hub ever sends them** -- confirmed with `grep -n "session_started" sim/live/fake_headset.py`
(zero matches) and cross-checked against `HubLiveRepository`, which already reads the *inner* `trial_event`
payload's `type` (`session_end`, not `session_started`/`session_ended`) for its own state machine, i.e. the
two halves of this app already disagreed about which vocabulary carries session lifecycle. Every message
(`status`, `trial_event`, ...) does carry the session in its own top-level `session_id` field per the schema,
and both the mock headset and (per `OpusSessionRunner.cs`'s description in `CONTEXT.md`) the real Unity runner
set it on every message -- so fixed `activeSessionId` tracking to derive from that field: set from `status`'s
`session_id` unless `state` is idle/finished/error (session over), and from `trial_event`'s `session_id`,
clearing on an inner `session_end` event. Kept the original dedicated-message-type handling as a fallback in
case a headset ever sends the literal wire type. Full reasoning + why the schema still lists those types is in
the code comment at `hub_connection.dart`'s `_onData`.

This was blocking task 2 and 6 outright: without it, `HubController.connectionForSession`/
`allRunningSessionIds()` (which every one of `MonitorHomeScreen`, `reports_list_screen.dart`'s "Live" badge,
and the patient profile's "Live now" pane depend on) could never find a live session from a real headset, no
matter what the UI showed.
